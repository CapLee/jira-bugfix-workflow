# 生产批量工作流（v2.5）

本轮只增加四项：分析资料包、批量续跑、修复推送门禁、重复写入保护。仍是 Python 标准库单文件，不需要服务或第三方依赖。

## 一、一次拿齐分析资料（只读）

从**业务项目目录**运行技能脚本的实际路径，不要为了找脚本切到工具目录，否则会改变项目配置发现位置。

```bash
python <技能目录>/scripts/jira.py triage STRUCTURING-123 STRUCTURING-124
python <技能目录>/scripts/jira.py triage --keys STRUCTURING-123,STRUCTURING-124 --format md --save analysis.md
python <技能目录>/scripts/jira.py triage --max 10
```

不传单号时按当前项目默认查询取前 10 张；显式单号只能同项目，重复单号自动去重，格式错误/跨当前项目会阻止。不会替用户跨项目查找。

每张包含详情、状态、经办人、报告人、评论、附件清单、变更历史、可用流转。默认不下载附件，也不改代码、不流转。

- 评论按实际 total 分页；历史在实例支持分页时继续获取。
- `total/fetched/complete` 表示完整性：实例不支持历史翻页或权限不足时明确标为不完整，不能据此说“没有更多评论/历史”。
- 单张失败保留其他单的资料，并返回 `errors` 与失败退出码。
- `selection.total/selected` 区分队列总数与本次选取数；资料包只覆盖选中的单，不代表整个队列已取完。

## 二、解决前先证明修复已推送

```bash
python <技能目录>/scripts/jira.py resolve STRUCTURING-123 \
  --repo <业务代码仓库> --fix-commit <实际修复SHA> \
  --impact '影响范围' --cause '本项目合法原因选项' \
  --solution '本项目合法解决方法' --prevention '本项目合法预防选项' \
  --assign reporter --dry-run
```

`<…>` 是说明用占位符，运行前替换成真实值，不能连括号一起填。字段选项以当前流转屏幕为准。

检查内容：
1. 指定代码仓库工作区干净（含未跟踪文件），不把不相关仓库误当交付证据。
2. 指定至少一笔实际修复 SHA（多笔重复 `--fix-commit`），不凭“HEAD 看起来已推送”猜修复归属。
3. 默认取当前分支上游，也可同时指定 `--remote origin --branch release`。
4. 现场 fetch 目标分支，确认当前 HEAD 和指定修复提交都在该远端分支历史中。
5. 认证失败、无法 fetch、无上游、未推送、工作区变化、修复提交不在目标分支，均停止流转。

**不会自动 commit/push。已推送不等于已部署，也不证明该提交确实修好了本单**：修复与单号的关联由人/AI 验证后提供；QA 构建是否包含修复仍需另核。团队共享工作区有他人未提交改动时，先整理交付或用干净检出验证，不允许清掉他人改动来通过门禁。

此为有意的行为变更：新版本正式 resolve 不再接受没有修复交付证据的“直接解决”；`--dry-run` 不带仓库/提交时仅探查字段，并明确标记交付尚未验证。已在 QA/终态的单只报跳过，不因门禁要求去重复流转。

## 三、批量处理并从失败处继续

### 1. 准备 JSON 清单

以下是**结构示例**，替换单号、仓库、提交 SHA 和本项目词表后使用；工具不会替你生成修复结论：

```json
{
  "action": "resolve",
  "repo": "<业务代码仓库>",
  "remote": "origin",
  "branch": "release",
  "issues": [
    {
      "key": "STRUCTURING-123",
      "fix_commits": ["<实际修复SHA>"],
      "impact": "本单影响范围",
      "cause": "本项目合法原因选项",
      "solution": "本项目合法解决选项",
      "prevention": "本项目合法预防选项",
      "field": ["BUG解决人=<实际登录账号>", "修复的版本=<实际版本>"],
      "assign": "reporter"
    }
  ]
}
```

- `action` 为 `start` 或 `resolve`；start 清单只需单号，不会自动做代码修复。
- resolve 的仓库/远端/分支可在每张单内覆盖；仓库相对路径以清单文件目录为基准。
- 不填 `assign` 或填 `reporter`：逐单读取报告人，不会固定转给某一个人。明确指定他人时需要用户授权。
- `comment` 可选；不填就不评论。字段值逐单明确填写，不复制别的单的修复结论。
- 未开始单自动接受后再读取解决屏幕；Working 单不重复接受；已交 QA/结束的单跳过。
- 批量不会自动接管别人的单。先取得授权并单独转派，重新规划后再执行。

### 2. 创建计划、预演、执行

```bash
python <技能目录>/scripts/jira.py batch plan --file batch-input.json
# 返回 task_file，以下替换为这个真实路径
python <技能目录>/scripts/jira.py batch run <任务文件>
python <技能目录>/scripts/jira.py batch run <任务文件> --execute
python <技能目录>/scripts/jira.py batch status <任务文件>
python <技能目录>/scripts/jira.py batch resume <任务文件> --execute
```

**plan、run/resume 不带 --execute 都不会写 JIRA。** 无修复证据的字段探查可单独用 `resolve KEY --dry-run`；批量 resolve 清单仍要求每单明确证据。 正式执行参数只能在用户明确授权本批流转后使用；“修一下/处理一下”不是流转授权。

计划只保存列表和快照，不承诺后续一定有权限流转。预演会读取当前字段及交付证据；未开始单的解决屏幕要等接受后才出现，因此预演会明确标注待二次校验，不能伪称整条已验证。

### 3. 失败恢复语义

- 写操作逐项串行；本地每步骤记录后再写 JIRA，写后读回精确核对状态/字段/经办人。
- 单张失败不吞掉其余单的结果；汇总 `done/skipped/failed`。
- 再次执行时重读成功项：仍一致则不写；被 QA 重开或被他人改动则报失败，不能重放旧任务。
- 请求确定被拒绝的剩余步骤可在修好权限/数据后继续。
- 同单同类操作存在未确认结果时，改变字段/更新时间也不能绕过；单独 resolve 改超时、配置文件路径等网络参数不会丢失原任务。交接恢复发现报告人或经办人变化立即停止，完成前再统一核对。
- **响应丢失、超时、5xx 等结果不确定时不会盲重试写入**：先读取 JIRA 确认是否已经完成；仍不确定则保持阻止。JIRA 不提供服务端幂等键，不能保证跨机器 exactly-once。
- 锁防止本机同一任务并行；异常退出可能留下锁。先确认旧进程已结束，再移除该任务提示的锁文件；不要删除执行记录重新碰运气。
- 任务绑定 JIRA 实例、账号、项目；切错环境或清单/日志损坏会阻止。

## 四、单命令重复执行保护

- `start`：已 Working/QA/结束，跳过。
- `resolve`：已 QA/结束，跳过；本工具曾只完成部分步骤时按持久化检查点核对，不能只看到 QA 状态就伪报完成。
- `comment`：相同当前作者+完整正文已存在则跳过；评论未取全则不发送。
- 附件上传：同名、同大小还要下载候选内容对比 SHA-256；同名但内容不同不会当成重复。
- 原始字段已是目标值仍需区分“只差流转”与“整个步骤已完成”；只有目标状态及字段全部匹配才跳过流转。

默认记录位置：`%LOCALAPPDATA%\hermes\jira-runs`（其它平台 `<用户目录>/hermes/jira-runs`），`JIRA_RUNS_DIR` 可改位置。记录含业务字段/评论，属于本机运行状态，**不要入库或发送给无权限人员**；不保存账号密码或认证头。
